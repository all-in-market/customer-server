## 들어가며

설계 자체는 좋다. 자가 호출(self-invocation) 위험 0건 — 전파 속성이 다른 로직을 전용 빈으로 철저히 분리했고, `@Transactional(readOnly = true)` 컨벤션이 15개 서비스에서 일관되며, LAZY 100%(EAGER·`@OneToMany`·cascade 0건), DTO record 100%, 재고 차감의 productId 정렬 락 + 원자적 조건부 UPDATE, 낙관적 락 + `@Retryable`/`@Recover`, 정산·지급의 유니크 제약 기반 멱등성까지 갖췄다.

문제는 **설계와 실제 코드가 벌어진 지점**이다. 아래 5개는 문서가 "이렇게 동작한다"고 기술한 것이 실제로는 동작하지 않거나 정반대인 항목들이다.

| # | 항목 | 성격 | 포트폴리오 설명력 |
|---|---|---|---|
| 1 | 스케줄러 전면 정지 + 아웃박스 자기 차단 | 시스템 정지 | ★★★ 원인 설명이 정교함 |
| 2 | 구매자/판매자 refresh 토큰 네임스페이스 공유 | 보안 (계정 탈취) | ★★★ 재현 가능한 취약점 |
| 3 | 재고 복구 lost update | 정합성 | ★★★ 재현 테스트가 곧 증거 |
| 4 | FK 인덱스 0건 | 성능 | ★★★ EXPLAIN + k6 전후 즉시 산출 |
| 5 | 테스트 지반 부재 (H2 스키마 이원화 + CI 정지) | 검증 전제 | ★★ 나머지 4개의 증거력을 결정 |

## 1. 스케줄러 9개가 전부 실행되지 않는다 + 켜는 순간 무한 대기

### 문제 A — 전면 정지

`src/main/java/com/example/allinmarket/AllInMarketApplication.java:7`

```java
import org.springframework.scheduling.annotation.EnableScheduling;

//@EnableScheduling          ← 주석 처리 (import는 5행에 남아 있음)
@SpringBootApplication
public class AllInMarketApplication {
```

프로젝트 전체에 `@EnableScheduling`이 **다른 어디에도 없다.** `git log` 확인 결과 `19c8fb1 feat: 스케줄링 처리 정지` (2026-05-10) 커밋으로 꺼진 뒤 3개월 이상 그대로다.

결과적으로 `common/scheduler`의 **7개 클래스 / 9개 `@Scheduled` 메서드가 하나도 실행되지 않는다.**

| 정지된 것 | 영향 |
|---|---|
| `OrderExpiryScheduler` | 30분 미결제 주문이 만료되지 않음 → **재고가 영구 점유** |
| `DashboardOutboxScheduler` | 결제는 성공하는데 **판매자 대시보드가 영원히 갱신 안 됨** |
| `HistoryOutboxScheduler` | 거래 이력 미적재 |
| `DailyStatisticsScheduler` | 일별 통계 미생성 |
| `SettlementScheduler` / `PayoutScheduler` | **정산·지급 파이프라인 전체 정지** |

`docs/ARCHITECTURE.md:152`는 *"ECS 멀티 인스턴스 환경이므로 모든 스케줄러가 모든 인스턴스에서 동시에 실행된다"*고 기술한다. **문서와 코드가 정면으로 불일치한다.**

### 문제 B — 켜면 터진다 (정지시킨 진짜 이유로 추정)

`common/scheduler/DashboardOutboxScheduler.java:26-30`

```java
@Scheduled(fixedDelay = 60000)
@Transactional                                          // ← 외부 트랜잭션
public void processOutbox() {
    List<DashboardOutbox> rows = repo.findTop100ForUpdate(pageable);   // PESSIMISTIC_WRITE, 100행 락
    for (DashboardOutbox row : rows) {
        dashboardOutboxService.processSingleEvent(row);                // REQUIRES_NEW
    }
}
```

호출 경로를 따라가면:

```
processOutbox()                    @Transactional        → 100행을 FOR UPDATE로 잠금
  └ processSingleEvent()           REQUIRES_NEW          → 외부 트랜잭션 서스펜드
      └ markProcessed()            REQUIRES_NEW          → saveAndFlush
          └ UPDATE dashboard_outbox SET processed = true WHERE id = ?
              ↑ 외부 트랜잭션이 FOR UPDATE로 잡고 있는 바로 그 행
```

내부 트랜잭션이 외부 트랜잭션의 락을 기다린다. 그런데 **외부 트랜잭션은 서스펜드된 채 애플리케이션 코드에서 내부 트랜잭션의 리턴을 기다린다.** 락 대기 순환이 DB에서 보이지 않으므로 **PostgreSQL 데드락 감지기가 잡지 못하고**, `application.yaml`에 `lock_timeout` 설정도 없어 **스케줄러 스레드가 영구 블로킹된다.**

관련 파일: `common/outbox/service/DashboardOutboxService.java:26,52`, `common/outbox/service/DashboardOutboxStatusService.java:15,24`, `common/outbox/repository/DashboardOutboxRepository.java:14-16`

### 이미 답이 리포 안에 있다

같은 리포의 `HistoryOutboxScheduler`는 **정확히 올바른 패턴**이다 — 스케줄러에 트랜잭션 없음 + `HistoryOutboxService.process(id)`가 REQUIRES_NEW 안에서 스스로 `findByIdForUpdate`. **두 아웃박스가 서로 다른 패턴인 것이 문제의 뿌리다.**

### 해결

1. `DashboardOutboxScheduler`에서 `@Transactional` 제거, `findUnprocessedIds(Pageable)`로 **ID만** 조회.
2. `processSingleEvent(Long id)`로 시그니처 변경 → REQUIRES_NEW 안에서 `findByIdForUpdate(id)` + `isProcessed()` 멱등 가드. `HistoryOutboxService`와 패턴 일치.
3. `DashboardOutboxStatusService`는 별도 REQUIRES_NEW가 불필요해지므로 흡수(중첩 트랜잭션 제거).
4. `@EnableScheduling`을 `SchedulingConfig`로 분리하고 `@ConditionalOnProperty("app.scheduling.enabled", matchIfMissing = true)` — local/k6 실행 시 끌 수 있게 해 **정지시켰던 원래 니즈를 살린다.**

### ⚠️ 재활성화 시 누적 백로그 (외부 리뷰 지적)

3개월 이상 정지했으므로 켜는 순간 미처리 아웃박스와 만료 대상 주문이 한꺼번에 쏟아진다. 특히 `OrderExpiryScheduler`는 100건씩 `do { } while (size == 100)`로 도는데 **내부에서 예외를 삼키므로 100건이 계속 실패하면 상태가 안 바뀌어 무한 루프**가 된다.

→ 주기당 처리 상한(`app.scheduling.outbox.chunk-size`, 기본 100)과 처리 기준일시 컷오프(`app.scheduling.cutoff-at`)를 프로퍼티로 노출하고, `do-while`에 최대 반복 횟수 상한을 건다.

### 검증

Testcontainers 통합 테스트: "미처리 아웃박스 1건 → 스케줄러 1회 실행 → 처리 완료". **수정 전 코드로 돌리면 타임아웃으로 실패하는 것**이 이 작업의 회귀 테스트다. 백로그 제어는 300건 삽입 후 chunk-size 100으로 3주기 소진 확인.

## 2. 구매자/판매자 refresh 토큰이 같은 Redis 키 공간을 쓴다 → 계정 탈취

### 문제

`buyer/auth/service/BuyerAuthService.java:81-117`
`seller/auth/service/SellerAuthService.java:93-128`

```java
// BuyerAuthService:81
redisTemplate.opsForValue().set("refresh:" + refreshToken, buyer.getId(), 7, TimeUnit.DAYS);
redisTemplate.opsForSet().add("user_refreshes:" + buyer.getId(), refreshToken);

// SellerAuthService:93  ← 완전히 동일한 키 포맷
redisTemplate.opsForValue().set("refresh:" + refreshToken, seller.getId(), 7, TimeUnit.DAYS);
redisTemplate.opsForSet().add("user_refreshes:" + seller.getId(), refreshToken);
```

두 페르소나가 `refresh:{token}`과 `user_refreshes:{userId}`를 **그대로 공유**한다. 저장 값은 **userId뿐이고 role 구분자가 없다.** `buyers`/`sellers`는 각각 독립 IDENTITY 시퀀스(`V1__init.sql`)라 **ID가 반드시 겹친다.**

### 터지는 시나리오

`SecurityConfig.java:32`에서 `/auth/**`는 `permitAll`이다.

```
1. 판매자(seller.id = 42)로 로그인 → Redis에 refresh:{tokenA} = 42
2. tokenA를 쿠키에 담아 POST /auth/refresh 호출        ← permitAll, 통과
3. BuyerAuthService.refresh()가 refresh:{tokenA}에서 42를 읽음
4. buyers.id = 42 (전혀 다른 사람) 의 BUYER access token 발급
```

→ **판매자 계정 하나로 임의의 구매자 계정을 탈취**할 수 있다.

역방향(`/seller/auth/refresh`)도 동일하다. 추가로 `user_refreshes:{userId}`도 공유되므로 **구매자 로그아웃이 동일 ID 판매자의 refresh 토큰을 전부 삭제**한다.

쿠키 `path`가 `/auth` vs `/seller/auth`로 나뉘어 있어(`BuyerAuthController.java:41`, `SellerAuthController.java:46`) 브라우저에서는 자연 발생하지 않지만, **서버가 강제하는 것이 아무것도 없다.** `docs/AUTH.md`에도 미기록.

### 곁들여진 문제 — `/auth/logout` 인가 비대칭

`common/config/SecurityConfig.java:29-40`

```java
.requestMatchers("/actuator/**").permitAll()
.requestMatchers("/auth/logout").authenticated()          // ← SELLER 토큰도 통과
.requestMatchers("/auth/**").permitAll()
.requestMatchers("/seller/auth/logout").hasRole("SELLER")  // ← 이쪽은 역할 검증
```

SELLER 토큰으로 `/auth/logout`을 호출하면 `BuyerAuthService.logout()`이 실행되어 **판매자 ID 기준으로 `user_refreshes:{id}`를 삭제**한다. 위 네임스페이스 충돌과 결합해 타인 세션을 무효화할 수 있다.

### 해결

1. 키 상수 클래스 신설(`common/auth/consts`, `final` + private 생성자) → `refresh:buyer:{token}` / `refresh:seller:{token}`, `user_refreshes:buyer:{id}` / `:seller:{id}`. 문자열 리터럴 연결 제거.
2. **하위 호환 dual-read**: 신규 키 miss 시 구 키(`refresh:{token}`)를 한 번 더 조회하고, 성공하면 신규 키로 이관 후 구 키 삭제. TTL 7일 후 제거할 임시 코드임을 주석과 `technical-decisions.md`에 명시.
3. `SecurityConfig.java:31` `/auth/logout` → `.hasRole("BUYER")`.

### 확인 필요

형제 서버(admin/chat 등)가 같은 Redis의 `refresh:` / `user_refreshes:` 키를 읽는지 확인해야 한다. 읽는다면 해당 리포도 함께 수정해야 하며, dual-read가 그동안의 안전망 역할을 한다.

### 검증

`BuyerAuthServiceTest` / `SellerAuthServiceTest`에 크로스-롤 refresh 거절 + dual-read 이관 케이스 추가. `docs/AUTH.md`의 Redis 키 표 갱신.

## 3. 재고 차감은 원자적인데 복구는 아니다 (lost update)

### 문제

`domain/product/repository/ProductRepository.java` — **차감은 원자적이다.**

```java
@Modifying(clearAutomatically = true)
@Query("UPDATE Product p SET p.stock = p.stock - :quantity " +
       "WHERE p.id = :productId AND p.stock >= :quantity " +
       "AND p.status = 'ON_SALE' AND p.deletedAt IS NULL")
int decreaseStockIfEnough(...);
```

`buyer/order/service/StockReleaseService.java:37-41` — **복구는 read-modify-write다.**

```java
List<OrderItem> orderItems = orderItemRepository.findAllByOrderIdWithProduct(order.getId());

orderItems.forEach(item ->
        item.getProduct().releaseStock(item.getQuantity())    // 읽고 → 더하고 → 더티체킹
);
```

`orderRepository.findByIdForUpdate(orderId)`로 **주문 행만** 잠근다. **Product는 잠그지 않는다.** 더티체킹이 만들어내는 SQL은 절대값 UPDATE다.

```
T1 (주문 생성)   : UPDATE products SET stock = stock - 3 WHERE id=1 AND stock >= 3   → 100 → 97
T2 (만료 복구)   : SELECT stock FROM products WHERE id=1   → 100 을 읽음 (T1 이전 스냅샷)
T2               : UPDATE products SET stock = 105 WHERE id=1     ← T1의 차감 3이 소실
```

`docs/technical-decisions.md`의 TD-002가 *"조건부 update는 Redis 락을 우회한 경로까지 막아 주는 최종 방어선"*이라고 기록한 원칙이 **복구 경로에는 적용되지 않았다.** 반쪽짜리 구조다.

### 해결

```java
// ProductRepository — 차감과 대칭
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("UPDATE Product p SET p.stock = p.stock + :quantity WHERE p.id = :productId")
int increaseStock(@Param("productId") Long productId, @Param("quantity") int quantity);
```

- `StockReleaseService`가 `Product.releaseStock()` 대신 이 메서드를 호출.
- 엔티티의 `releaseStock()`는 제거하거나 테스트 전용으로 축소한다. **setter 경로가 남으면 같은 실수가 재발한다.**
- `decreaseStockIfEnough`에도 `flushAutomatically = true` 추가 — 현재 기본 false라 벌크 UPDATE 전 플러시 보장이 없다.

### 지켜야 할 제약 (외부 리뷰에서 "멱등 가드가 없다"는 지적이 나왔으나, 실제로는 이미 있다)

`StockReleaseService`는 이미 중복 복구를 막고 있다.

```java
Order order = orderRepository.findByIdForUpdate(orderId).orElseThrow(...);   // 주문 행 잠금
if (order.getStatus() != OrderStatus.CREATED) {                              // 멱등 가드
    return;
}
...
order.fail();                                                                // 같은 트랜잭션에서 상태 전이
```

**이 순서와 가드를 절대 건드리지 않는다.** 별도 `restock_status` 컬럼이나 `max_stock` 상한은 스키마 비용 대비 이득이 없으므로 추가하지 않는다. 이 판단 근거를 `technical-decisions.md`에 TD로 남긴다.

### 곁가지 — `clearAutomatically`의 부작용

`BuyerOrderService.createOrder`가 차감 루프(매 호출마다 영속성 컨텍스트 clear) **이후에** `cartItemRepository.deleteAll(cartItems)`를 호출한다. cartItems가 이미 준영속 상태라 Spring Data가 `em.merge()`를 거치며 **아이템당 SELECT가 추가로 나간다.** 별도 작업으로 분리.

### 검증

`BuyerOrderConcurrencyTest`에 "동시 주문 차감 + 만료 복구" 시나리오 추가. **수정 전 코드에서 반드시 실패하는지 먼저 확인**한다. 단, 5번 항목(Testcontainers 전환) 이후에 검증해야 의미가 있다 — H2에서는 재현되지 않을 수 있다.

## 4. 커머스 핵심 테이블에 FK 인덱스가 하나도 없다

### 문제

PostgreSQL은 **FK에 인덱스를 자동 생성하지 않는다.** 그런데 `V1__init.sql`(431줄, 13개 테이블) 안에 **`CREATE INDEX`가 단 한 줄도 없다.**

전체 마이그레이션에서 `CREATE INDEX`가 등장하는 것은 V5·V6(부분 유니크), V7(아웃박스 폴링), V13(payouts), V14(채팅), V15(재입고 알림), V17(langchain4j trgm), V18(상품 이미지)뿐이다. **커머스 핵심 테이블은 전부 비어 있다.**

| 인덱스 없는 컬럼 | 이 컬럼을 타는 쿼리 |
|---|---|
| `orders.buyer_id` | `findByBuyerId` — 구매자 주문목록, 페이징 |
| `order_items.order_id` | `findAllByOrderIdWithSeller` / `WithProduct` |
| `order_items.seller_id` | `findAllBySellerId` — 판매자 주문목록, 페이징 |
| `products.seller_id` | `findAllBySellerIdAndDeletedAtIsNull` — 판매자 상품목록 |
| `products.category_id` | 카테고리 필터 |
| **`payments.order_id`** | `findByOrderIdAndStatusForUpdate` — **`FOR UPDATE`인데 인덱스가 없어 스캔하며 락을 건다** |
| `cart_items.cart_id`, `.product_id` | `findByCartId`(페이징), `findByCartIdAndProductId` |
| `addresses.buyer_id` | `findAllByBuyerId` |
| `refunds.buyer_id` | `findAllByBuyerId`(페이징) |
| `settlements.seller_id` | `findAllBySellerId`(페이징) |
| `payouts.seller_id` | FK |
| `restock_subscriptions.product_id` | 재입고 팬아웃 (유니크 인덱스 선두가 `user_id`라 못 씀) |

추가로 `orders(status, created_at)` 복합 인덱스가 없어, `OrderExpiryScheduler`가 **1분마다 도는** `findByStatusAndCreatedAtBefore`가 orders 전체 스캔이다.

`common/initializer/dummy/DummyDataService.java`(708줄)로 **100만 상품 / 30만 주문** 더미를 생성하는 프로젝트다. 대용량 실험이 목적인데 그 규모에서 위 인덱스 부재는 즉시 체감된다.

### 함께 발견된 것

`RestockNotification` 엔티티는 `uk_restock_notification_user_product(user_id, product_id)`를 선언하는데 **`V15`에 해당 인덱스가 없다.** `ddl-auto: validate`는 유니크 제약을 검증하지 않으므로 조용히 통과하고, **DB에서 중복 알림이 막히지 않는다.** (같은 성격인 `restock_subscriptions`는 V12에 제대로 있다.)

### 해결

`V19__add_foreign_key_indexes.sql`
- 위 12개 + `orders(status, created_at)`.
- 소프트 삭제 컬럼이 거의 모든 조회에 붙으므로 해당 테이블은 `WHERE deleted_at IS NULL` **부분 인덱스**로.
- 누락된 `uk_restock_notification_user_product`도 함께 추가.

### ⚠️ 운영 적용 런북 (외부 리뷰 지적 — 코드가 아니라 문서로)

대용량 테이블에 `CREATE INDEX CONCURRENTLY`를 Flyway로 돌리면
(a) 트랜잭션 밖 실행이라 다른 ECS 인스턴스가 Flyway advisory lock 타임아웃으로 **기동 실패**할 수 있고,
(b) 중간 실패 시 인덱스가 `INVALID` 상태로 남아 재실행이 "already exists"로 **영구 실패**한다.

현재 상시 가동 환경이 없으므로 마이그레이션은 일반 `CREATE INDEX`로 두되, 운영 적용 절차(사전 수동 `CONCURRENTLY` 실행 → Flyway `baseline`/`IF NOT EXISTS` 처리 → `pg_index.indisvalid` 확인)를 `technical-decisions.md`에 기록한다. **이 판단 자체가 포트폴리오 서술 소재다.**

### 검증 — 이 항목이 측정 근거를 만들기 가장 쉽다

```bash

# application-local.yml 에서 dummy enabled=true → 100만 상품 / 30만 주문 시드
docker compose exec -T redis redis-cli --scan --pattern 'products:search:*' \
  | xargs -r docker compose exec -T redis redis-cli DEL      # TR-002 재발 방지
docker compose -f docker-compose-k6.yml up --abort-on-container-exit
```

- 적용 전후 `EXPLAIN (ANALYZE, BUFFERS)` 비교 (Seq Scan → Index Scan, Buffers 감소)
- `k6/scenario-b.js`(상품 목록), `scenario-e-order.js`(주문, `order_duration_ms`) p95 비교
- **측정 환경을 결과에 명시한다** — 로컬 Docker Compose이지 RDS가 아니므로 절대 수치가 아니라 **상대 개선폭**으로 서술하고, Hikari 20 / `max_connections` 기본값 조건도 함께 기록한다.
- 결과는 `docs/improvement/`에 기록 (CLAUDE.md: 그래프·시각화는 README가 아니라 여기).

## 5. 나머지 4개를 증명할 지반이 없다 — H2 스키마 이원화 + CI 정지

앞의 1~4번은 **전부 락·동시성·인덱스** 이야기다. 그런데 현재 테스트 환경으로는 그중 어느 것도 증명할 수 없다.

### 문제 A — 운영 스키마와 테스트 스키마가 서로 다른 두 개

`src/test/resources/application-test.yml`

```yaml
url: jdbc:h2:mem:testdb;MODE=PostgreSQL
ddl-auto: create-drop
flyway:
  enabled: false          # ← Flyway를 끄고 Hibernate가 스키마를 새로 만든다
```

즉 **운영은 Flyway V1~V18, 테스트는 Hibernate 자동 생성**이다. 다음 중 어느 것도 테스트에서 검증되지 않는다.

- 부분 유니크 인덱스 2개 (`ux_address_default`, `uq_payments_order_success`) — 이 프로젝트 정합성 설계의 핵심
- CHECK 제약, `pg_trgm` / `vector` 확장, `timestamptz` 컬럼
- FK 인덱스 (4번 항목)
- **`FOR UPDATE` / `SKIP LOCKED` / MVCC 격리 의미론** (1번·3번 항목)

특히 `BuyerOrderConcurrencyTest`는 재고 1개에 두 스레드가 주문해 1성공/1실패를 검증하는데, **행 잠금 의미론이 PostgreSQL과 다른 H2 인메모리에서 통과한 것**이라 원자적 재고 차감의 증거로는 약하다. `@MockitoBean RedissonClient`로 분산 락도 무력화된 상태다(DB 레벨만 보려는 의도는 이해되나 명시적 문서화가 없다).

**의존성은 이미 다 들어와 있다** — `testcontainers-bom:1.21.3` + `junit-jupiter` + `postgresql`. 실제로 쓰는 건 `FlywayMigrationTest` 하나뿐이다.

### 문제 B — CI가 꺼져 있다

`.github/workflows/ci.yml`

```yaml
#name: CI
#on:
#  push:
#    branches: [ main, dev ]
#  pull_request:
#    branches: [ main, dev ]
```

**파일 전체가 주석 처리되어 있다.** PR에서 빌드도 테스트도 돌지 않는다. 최근 커밋 5개가 전부 `test:` 접두사인데 정작 게이트가 없다. 커버리지 측정 수단(jacoco)도 없다.

### 문제 C — REST Docs 산출물이 비어 있다

`build.gradle:114-117`

```gradle
asciidoctor {
    inputs.dir snippetsDir
    dependsOn test
}
```

`sourceDir`가 없다. asciidoctor-gradle 플러그인의 기본 소스 디렉터리는 **`src/docs/asciidoc`**인데, 실제 `.adoc` 18개는 **`docs/asciidoc/`**에 있고 `src/docs/` 디렉터리는 **존재하지 않는다.**

→ `asciidoctor` 태스크가 입력 0개로 NO-SOURCE 성공하고, `bootJar`가 `static/docs`에 **빈 디렉터리를 번들**한다. TRD §12가 기술한 "REST Docs를 배포 산출물에 번들"이 **실제로는 일어나지 않고 있다.**

### 해결

1. **Testcontainers PostgreSQL 전환** — `spring-boot-testcontainers` 의존성 추가(현재 없음), `@ServiceConnection` 기반 컨테이너 베이스 클래스 신설. 이미지는 **`pgvector/pgvector:pg16`** (V9의 `CREATE EXTENSION vector` 때문 — TD-001/TR-001). `application-test.yml`에서 Flyway 활성화, H2 제거. `testcontainers.reuse.enable=true`로 빌드 시간 방어(`bootJar → asciidoctor → test` 체인이라 테스트 시간이 곧 배포 시간이다).
2. **CI 워크플로 복구** + jacoco. `FlywayMigrationTest`가 `@Testcontainers(disabledWithoutDocker = true)`라 **Docker가 없으면 조용히 스킵**되므로, CI에서 스킵 여부를 명시적으로 검사한다.
3. **`asciidoctor { sourceDir file('docs/asciidoc') }`** 추가. 빌드 후 jar 안에 실제 HTML이 들어가는지 확인.

### 왜 이것이 1번이어야 하는가

외부 리뷰의 가장 강한 지적이 이것이었다. **락과 동시성 수정(1번·3번)을 H2에서 검증한 뒤 나중에 재검증하는 순서는 증거력이 없다.** H2에서 통과하고 PostgreSQL에서 데드락이 나는 경우를 잡을 수 없다.

→ **실행 순서상 5번 항목을 가장 먼저 한다.** 그다음 1 → 3 → 2 → 4 순으로 진행하면, 각 수정마다 "수정 전 코드에서 실패하고 수정 후 통과하는 테스트"를 실제 PostgreSQL 위에서 남길 수 있다.

## 이번 TOP 5에서 제외했지만 기록해 둘 것

아래는 조사에서 확인된 실제 문제이지만 위 5개보다 우선순위가 낮다.

- **`/actuator/**` 전면 `permitAll`** — `metrics`·`prometheus` 포함 무인증 노출. TRD §14에 이미 "알려진 제약"으로 기록되어 있으나 미조치.
- **`open-in-view` 미설정(기본 true)** + `reWriteBatchedInserts=true`를 걸어놨는데 `hibernate.jdbc.batch_size`가 없어 **JPA `saveAll()`이 전혀 배치되지 않음**. `show-sql` 기본값도 true라 운영 로그 오염.
- **`GlobalExceptionHandler` 누락 핸들러 7종**이 `Exception.class`에 삼켜져 전부 500 — `?sort=없는필드` 하나로 **11개 페이징 엔드포인트가 전부 500**을 뱉는다. `spring.data.web.pageable.max-page-size` 미설정으로 `?size=1000000`도 가능.
- **컨트롤러 테스트 17/17이 레거시 `RestDocsControllerTest` 상속**(CLAUDE.md는 "복제하지 않는다"고 명시, 채택률 0%)이고 **`springSecurity()`가 적용되지 않아 인가 규칙 테스트가 0건**. 권한 문자열도 `"SELLER"`(ROLE_ 접두어 없음)라 시큐리티가 붙었다면 전부 실패할 값이다.
- **`domain.*` 리포지토리 4개가 `seller.dailystatistics.dto`를 import**하는 역방향 레이어 의존. 반대로 `buyer → seller` 위반은 `BuyerPaymentService`의 **한 번도 호출되지 않는** `DashboardService` 필드 하나뿐이라, **그 줄만 지우면 0이 된다.**
- **데드 코드**: Kafka 의존성(autoconfig exclude + 사용 0), `@RedisLock`/`RedisLockAspect` 113줄(사용처 0인데 구현 품질은 좋다), `AsyncConfig.dashboardExecutor`(`@Async` 사용 0 — 마침 `RestockEventListener`가 동기 실행이라 알림 HTTP 4회 재시도가 API 응답 스레드를 점유하고 있으므로 여기 쓰면 된다), `ErrorEnum` 79개 중 미사용 11개 + HTTP 상태 매핑 오류 7건.
- **캐시**: 4개 서비스가 `@Transactional(readOnly = true)` **안에서** Redis를 왕복해 캐시 히트가 DB 커넥션을 점유한다(Hikari 20). `SellerProductService`는 쓰기마다 `products:search:*` **SCAN 무효화**를 도는데, 같은 리포의 `SellerSettlementService`가 이미 version-key `INCR` 무효화를 쓰고 있다.
